# Principled Simplicity — Abstraction Readiness / 抽象成熟度评分

> **何时加载 / Load this when:** 用户问「这个 pattern 我见了几次，要建机制吗？」「现在抽象会不会太早？」——即**该不该抽象、值不值得抽象**这类判断题。

**核心前提：** 抽象太早制造复杂度债；抽象太晚制造补丁债。评分让这个判断显性化，而不是凭感觉。

---

## 5 个维度 / Five Dimensions

每个维度打分 1–3，总分 5–15。

### 维度 1：频率 / Frequency

**这个 pattern 实际出现了多少次？**

| 分 | 标准 |
|---|---|
| 1 | 1–2 次，可能是巧合 |
| 2 | 3–5 次，分散在不同时间或场景，有共因 |
| 3 | ≥6 次，或在高流量路径上规律出现 |

> 不要把「我能想到 5 个未来可能的 case」算进去——那是想象，不是数据。只数**实际发生过**的。

### 维度 2：变体 / Variation

**同一底层意图，有多少种不同的表达方式？**

| 分 | 标准 |
|---|---|
| 1 | 1 种表达，case 之间几乎一模一样 |
| 2 | 2–4 种表达，差异在表层（字面、措辞） |
| 3 | 5+ 种，或表达方式开放不可枚举（自然语言意图） |

> 这个维度本质上回答：**写规则能不能覆盖完？** 能枚举 → 规则够；不能枚举 → 需要机制（模型）。

### 维度 3：维护痛苦 / Pain

**不抽象、继续打补丁的代价是什么？**

| 分 | 标准 |
|---|---|
| 1 | 痛苦极小：1 处补丁，几乎没有连锁影响 |
| 2 | 痛苦明显：补丁互相干扰、回归风险高，或已有过生产事故 |
| 3 | 痛苦严重：每次修复都伴随旧 case 退化，团队持续抱怨 |

> 信号词：「上次修这个又把那个搞坏了」「只有 X 知道这块」「每次改这里都要小心」→ 2 分以上。

### 维度 4：复用面 / Reusability

**这个机制如果建出来，有多少调用方能复用？**

| 分 | 标准 |
|---|---|
| 1 | 仅 1 个调用方，且无第二个的迹象 |
| 2 | 2–3 个调用方，或 1 个 + 明确的近期需求 |
| 3 | ≥4 个调用方，或属于平台级 / 跨产品线能力 |

> 陷阱：不要用「理论上可以被很多东西复用」打高分——**只数有名字的明确调用方**。

### 维度 5：清晰度 / Clarity

**机制的边界现在说得清吗？**

| 分 | 标准 |
|---|---|
| 1 | 仍不清晰：新变体持续让团队意外，现在抽象很可能需要立即返工 |
| 2 | 基本清晰：核心形状稳定，少量 edge case 还在浮现 |
| 3 | 清晰且稳定：团队能说出机制该处理什么、该拒绝什么、怎么测试 |

## 总分解读 / Score Interpretation

| 总分 | 行动 |
|---|---|
| **5–7** | **观察。** 记录 case，设触发条件（如「出现第 4 次时重新评估」），打最小化补丁。现在抽象 = 过早抽象。 |
| **8–10** | **轻量提取。** 抽个公共函数、共享 prompt 片段、统一数据结构即可。重点是让下次出现时容易识别为同类。 |
| **11–13** | **投资建机制。** 走完整 Step 5 六字段规格，配 eval plan，显性分配 model/code/eval 责任。这是 Principled Simplicity 的主战场。 |
| **14–15** | **可能要建 Skill 或平台能力。** 这种复用面 + 痛苦，通常意味着的不只是机制，而是团队层共享资产。 |

## 强制覆盖 / Override Rules

**无论评分，立即抽象：**
```
[ ] 涉及安全或权限边界（安全检查不能活在散落的 if/else 里）
[ ] 同一个 bug 被修了超过一次（重复修复 = 机制缺口已被证实）
[ ] 逻辑跨越系统边界（两个模块实现同一检查 = 架构问题）
```

**无论评分，暂缓抽象：**
```
[ ] 团队还说不清一个负例（说不清该拒绝什么 = 边界未稳定）
[ ] 这段代码即将被替换（为注定消亡的路径建抽象 = 浪费）
[ ] 没有 owner（无人维护的抽象会腐化成更坏的补丁）
```

## 反向使用：删除现有抽象 / Reverse Use

这个评分**也可以反向用**——评估已有抽象现在是否应该被删除。

把现有抽象当作「假想待建项」重新打分。如果总分降到 7 以下：
- 频率消失（场景变了，这个机制没人用）
- 变体收窄（其实写规则就够，不再需要机制）
- 维护痛苦反转（机制本身比它消除的补丁还痛）
- 复用面消失（从来就只有一个调用方）

**删除一个不再需要的抽象，本身就是大道至简。**

## 决策记录模板 / Decision Log

每次用本评分做决策，写一行记录。下次同类问题来时可以快速对照。

```
日期:    [YYYY-MM-DD]
对象:    [pattern / mechanism 名称]
评分:    Frequency [N] · Variation [N] · Pain [N] · Reusability [N] · Clarity [N] = [总分]
决策:    [观察 / 轻量提取 / 建机制 / 建 skill]
原因:    [一句话]
复评时间: [何时回来重新评估]
```

## 例子 / Example

**场景：** Agent 过去三个月有 4 次工具选择失败，都是把"找文件"的请求路由到了 web_search。每次修复都加一条关键词规则。

```
Frequency:  2  (4 次，有共因)
Variation:  3  ("找文件"在用户语料里有十几种说法，无法枚举)
Pain:       2  (现在堆了 6 条关键词规则，互相覆盖，新 case 来了不知道改哪条)
Reusability: 2  (搜索路由、工具路由也有类似问题，可复用)
Clarity:    2  (核心形状清晰：source-of-truth disambiguation；少量 edge case 还在浮现)

总分:       11  → 投资建机制

Override:   同一 bug 被修了 4 次 → 立即抽象
```

→ 行动：建 `ToolRoutingArbiter`，走完整六字段规格，配 eval plan（覆盖现有 4 个 case + 各种新变体）。
